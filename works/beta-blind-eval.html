베타 테스터 블라인드 평가 툴

외부 베타 테스터가 조건을 모른 채 두 모델을 비교하고, 운영자가 "배정한 조건 = 실행된 조건"을 서버로 보장하는 블라인드 평가 도구. 기획 · 데이터 모델 · FastAPI 백엔드 · 운영자/테스터 화면까지 단독 개발했고, 사내 전용이던 앱을 외부에 열기 위한 접근 제어 계층도 함께 얹었다.

  • 기간2026.08 (1개월)
  • 소속(주)버블탭 AI코어팀
  • 역할단독 기획·설계·개발
사용 기술

FastAPIPostgreSQLSQLAlchemyAlembicReact(Vite + TypeScript)

문제#

모델이나 프롬프트를 개선할 때 QA를 내부 인원만 할 수 있었다. 외부 사용자를 대상으로, 그것도 어느 쪽이 어떤 모델인지 모르는 상태에서 비교를 돌릴 수단이 없었다.

  • 테스트 세팅(모델·프롬프트 버전·캐릭터·파라미터)이 각 테스터의 브라우저(localStorage)에만 남는다. 운영자가 실험 조건을 통제할 수도, 실제 그 조건으로 대화가 이뤄졌는지 확인할 수도 없다 — 이 상태로는 어떤 비교 결과도 신뢰할 수 없다.
  • 조건을 화면에서 감추는 것만으로는 부족하다. 개발자 도구를 열 줄 아는 테스터는 임의 모델·버전으로 요청을 바꿔 보낼 수 있어, "배정한 조건"과 "실행된 조건"이 갈라지면 수집 데이터 전체가 쓸모없어진다.
  • 사내 전용 앱이라 없던 접근 제어를, 외부 테스터에게 열기 전에 갖춰야 한다 (아래 참조).

설계의 축 — 새로 만들지 말고 옮긴다#

조사해 보니 "설정 세트" 개념이 이미 프론트엔드 설정 파일에 완성돼 있었다 — 모델·프롬프트 버전·파라미터·모드 등 채팅 화면이 소비하는 실험 세팅 전부가 스키마 하나에 들어 있었다. 문제는 저장 위치가 localStorage라는 것뿐이었다.

새로 만든 것   설정 세트 · 배정 · 접근 제어 계층 · 조건 강제 게이트 · 운영자/테스터 화면
그대로 둔 것   채팅 렌더 로직 · 대화 저장 테이블 · CSV 추출

핵심은 그 스키마를 DB로 올려 계정에 귀속시키는 것이었다. 채팅 파이프라인은 손대지 않는다.

데이터 모델#

테이블역할설계 판단
qa_test_sets재사용 가능한 설정 세트 — 캐릭터·모델·프롬프트 버전·모드·샘플링 파라미터·최소/최대 턴컬럼명을 기존 프론트 설정 스키마와 일치시켜 변환 코드를 0으로. 비교 축이 아닌 필드(요약 주기 등)는 지금 넣지 않고 필요해지면 컬럼 추가로 늘린다
qa_assignments계정 ↔ 세트 N:N 배정 — 상태(pending / in_progress / done), 연결된 방세트 정의와 배정을 분리해 한 세트를 여러 테스터에게. room_id에 부분 유니크 인덱스(조건: room_id IS NOT NULL) — 한 방이 두 과제에 묶이면 조건 강제 게이트가 어느 배정을 적용할지 결정할 수 없다
users (확장)role(tester / admin), access_token기존 컬럼 불변. role 서버 기본값을 최소 권한(tester)으로 둬, role을 빠뜨린 INSERT가 admin이 되지 않게
  • 채팅 방은 기존 chat_rooms를 한 컬럼도 안 바꾸고 재사용했다. 대화 저장·복원·CSV 다운로드·요청 원문(request_body) 보존이 전부 딸려 오고, 역참조만 qa_assignments.room_id로 건다.
  • Alembic 마이그레이션 두 벌 — 하나는 users 확장(기존 계정을 admin으로 백필 + 토큰 발급), 하나는 QA 테이블 신설. 둘 다 기존 스키마를 건드리지 않는 순방향 변경으로 짰다.

API#

테스터용  (X-User-Id + X-Auth-Token)
  POST  /auth/login                로그인 — 승인제(미등록 ID·토큰 불일치는 거부)
  GET   /qa/my-sets                배정된 세트 카드 (상태 · 턴 수 · min/max)
  GET   /qa/assignments/{id}       세트 전체 설정 + 방 (없으면 생성해 반환)
  POST  /qa/assignments/{id}/complete   최소 턴 미달이면 400

운영자용  (관리자 전용)
  CRUD  /qa/sets                   설정 세트
  CRUD  /qa/testers                ID 발급 + 토큰 생성 + 세트 배정
  GET   /qa/results                테스터 × 세트 진행 현황
  GET   /qa/assignments/{id}/csv   과제 1건
  GET   /qa/sets/{id}/csv          세트 전체 합본 (앞에 tester_id · set_name 열 추가)
  • 진행 턴 수는 서버가 대화 테이블에서 직접 센다. 프론트 상태로 세면 새로고침에 취약하고 조작된다 — 완료 버튼이 열리는 최소 턴, 대화가 잠기는 최대 턴 모두 같은 서버 계산을 쓴다.
  • 로그 추출은 새로 만들어야 했다. 기존 GET /rooms/{id}/csv는 소유자 전용이라 남의 방은 404다. 운영자가 테스터 대화를 뽑는 QA 전용 추출 엔드포인트를 별도로 뒀다.

화면#

  • 운영자 — /prompts/qa 한 페이지에 탭 3개(설정 세트 / 테스터 발급·배정 / 진행 현황). 탭 전환은 URL을 바꾸지 않는다(화면 내 상태). 발급 토큰은 그 화면에서 딱 한 번만 보인다.
  • 테스터 — 3화면(세트 카드 목록 → 블라인드 대화 → 완료)이 전부. /·/create·/prompts 진입 시 /qa로 되돌린다. 세트는 아무 순서나 고르고, 중단 후 재개할 수 있다.
  • 채팅 화면은 678줄짜리 기존 컴포넌트를 복제하지 않고 속성 4개(설정 주입 · 방 ID · 사이드바 숨김 · 상단바)만 추가해 재사용했다. 버전 정책의 pinned가 이미 구현돼 있어 고정 버전이 그대로 물린다.

블라인드 평가 흐름#

운영자
  │  설정 세트 정의 · 테스터 계정 발급(ID + 액세스 토큰) · 세트 배정
  ▼
테스터
  │  받은 ID·토큰으로 로그인 → 배정된 세트 목록 (순서 자유)
  │  좌우 두 대화창에 같은 입력 — 어느 쪽이 어떤 모델인지 모름
  │  "어느 쪽이 더 나은가"만 판단, 최소 턴을 채우면 완료
  ▼
운영자
  │  진행 현황 표에서 테스터 × 세트별 상태·턴 수 확인
  │  대화 로그 CSV 회수 (과제 1건 / 세트 전체 합본)

평가 점수는 툴 안에서 받지 않는다. 별도 채널(문서)로 수집하고, 툴은 대화 로그 회수까지만 책임진다 — 평가 입력 UI를 넣지 않기로 한 결정이다.

기술 의사결정#

"배정한 조건 = 실행된 조건"을 서버가 보장한다#

프론트에서 설정 UI를 감추는 것만으로는 부족하다. 채팅 API 진입부에 게이트를 하나 두고, 테스터 역할의 요청이면 방에 묶인 배정을 조회해 모델·버전·모드·파라미터를 대조한다. 하나라도 다르면 403.

덮어쓰기가 아니라 거부다. 서버가 조용히 배정값으로 덮어쓰면 데이터 정합성은 더 강하지만, 목록 화면이 잘못된 버전을 넘겨도 아무도 모른 채 평가가 끝난다. 거부하면 개발 중에 즉시 드러나고, 운영 중엔 위조 시도가 로그에 남는다.

턴 상한은 제한이 아니라 비교 공정성 장치#

세트 A를 10턴, 세트 B를 50턴 대화하면 두 세트는 더 이상 같은 조건이 아니다. 턴 수가 임계치를 넘으면 장기기억 요약이 돌아 그 결과가 프롬프트에 들어가고, 대화 히스토리가 잘리는 지점도 달라진다 — 턴 수 차이가 실제 프롬프트 내용을 바꾼다.

상한이 없으면 "모델 A가 더 좋았다"가 모델 차이인지 대화 길이 차이인지 구분되지 않는다. 그래서 최대 턴에 도달하면 입력창을 잠그고 서버도 403으로 막는다. 자유 대화가 필요한 세트는 상한을 비워 두면 무제한이 된다.

외부 공개에 필요한 접근 제어 계층#

이 앱은 사내 개발자만 쓰던 도구라, "너 누구야"(신원 확인)까지만 있고 "너 그거 해도 돼"(권한)는 묻지 않았다. 계정도 로그인 창구에서 자유롭게 만들 수 있었다. 내부 전용일 때는 그걸로 충분했지만, 외부 테스터를 처음 들이면 사정이 달라진다 — 로그인만 하면 다음이 전부 조회·수정 가능하다:

  • 시스템 프롬프트 원문
  • 캐릭터의 비공개 설정 전문
  • 서빙 중인 프롬프트 교체·삭제
  • 렌더 API — 응답에 시스템 프롬프트를 통째로 반환

QA 토큰을 아무리 잘 만들어도 이쪽이 열려 있으면 의미가 없다. 그래서 접근 제어 계층을 QA 기능보다 먼저 얹었다.

  • 역할을 tester / admin 둘로 고정하고, 기존 신원 확인 위에 관리자 전용 검사를 한 겹 얹는 방식 — 라우트별 변경이 한 줄
  • 라우트 파일 여러 곳에 흩어져 있던 인증 의존성을 한 모듈로 통합
  • 계정을 자유 가입에서 발급제로 전환. 토큰은 로그인 때만이 아니라 매 요청에 검증 — ID만 알면 API가 뚫리는 걸 막는다
  • 토큰 비교는 상수 시간 비교로 — 응답 시간 차로 토큰을 한 글자씩 맞춰 나가는 시도를 차단
  • 렌더 API와 프롬프트 조회는 반드시 함께 막는다 — 한쪽만 막으면 다른 쪽으로 원문이 샌다

비대화형 접근은 새 인증 수단 대신 서비스 계정으로#

MCP 서버·스크립트 같은 비대화형 호출을 위해 별도 키를 만들자는 초안을 철회했다. 관리자 권한을 가진 서비스 계정을 발급해 그걸로 붙이면 충분하다 — 발급·폐기가 일반 계정 관리와 똑같아지고, 변경 주체가 기록에 남는다.

잠그지 못한 것#

캐릭터 이미지 같은 바이너리는 <img> 태그로 소비되어 커스텀 헤더를 실을 수 없다. 닫으려면 프론트를 fetch 방식으로 바꿔야 해서 이번 범위 밖으로 두되, 노출되는 것이 이미지뿐이고 프롬프트·설정은 새지 않음을 확인했다.

결과#

  • 운영자 발급 → 세트 배정 → 블라인드 대화 → CSV 회수의 전 과정을 단독 구현해 실험 조건을 배정 단위로 통제할 수 있게 만들고, 사내 배포 후 외부 베타 테스터에게 공개
  • 사내 인원과 외부 모집 테스터가 1차 블라인드 평가 라운드 진행, 수집 로그를 모델·프롬프트 채택 판단 자료로 회수
  • 외부 공개에 맞춰 전 엔드포인트에 역할 기반 접근 제어를 적용 — 최종 가드 배치 관리자 전용 32 · 로그인 필요 17 · 공개 6
