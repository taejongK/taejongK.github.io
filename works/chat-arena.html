Chat Arena

모델·프롬프트 버전의 우열을 사람의 블라인드 쌍대 비교로 정하고, 쌓인 표를 Bradley-Terry 모델로 하나의 점수 척도에 올리는 평가 도구입니다.
표를 모으고 점수로 바꾸는 방식에 설계의 무게를 뒀습니다.

문제#

모델·프롬프트 버전을 같은 맥락에서 사람이 비교한 데이터가 없었습니다.
기존 사내 아레나는 프롬프트를 자체 코드로 조립해 실제 서빙 응답과 다른 응답을 비교하고 있었습니다.

  • 무엇을 비교하는가: 아레나 응답이 실제 서비스 응답과 같아야 합니다.
  • 어떻게 점수로 바꾸는가: 기준이 제각각이고 고르지 않게 쌓인 표를 흔들리지 않는 순위로 바꿔야 합니다.

이 페이지는 주로 두 번째, 평가 방법론을 다룹니다.

왜 절대 점수가 아니라 쌍대 비교인가#

  • 5점 척도 같은 절대 평가는 평가자마다, 앞서 본 응답마다 기준점이 움직입니다.
  • 두 응답 중 하나를 고르게 하면 평가자 고유의 기준점이 상쇄되고, 비교적 일관된 상대 정보만 남습니다.
  • 이 승패 목록을 전체 순위로 바꾸는 역할을 Bradley-Terry가 합니다.

Bradley-Terry 모델#

각 참가자 i에게 보이지 않는 강도 p_i(> 0)가 있다고 두고, 승률을 다음처럼 가정합니다.

P(i가 j를 이김) = p_i / (p_i + p_j)

로그 척도로 쓰면  θ_i = log p_i
P(i가 j를 이김) = 1 / (1 + exp(-(θ_i - θ_j)))     ← 점수 차의 로지스틱 함수

승률은 점수 차이에만 의존하므로, 직접 붙지 않은 참가자도 공통 상대를 거쳐 비교할 수 있습니다.
절대 위치에는 의미가 없어 한 점을 고정하는 정규화가 필요합니다.

Elo가 아니라 Bradley-Terry를 택한 이유#

Elo는 온라인 갱신이라 표가 들어온 순서와 갱신 폭(K)에 따라 결과가 달라집니다.
Bradley-Terry는 쌓인 표 전체로 가능도를 최대화하는 배치 추정이라 순서와 무관합니다.
평가 데이터는 "지금까지 모은 판정 전체"이므로 이쪽이 맞다고 판단했습니다.

추정: MM 반복#

승수 W_i와 대결 횟수 n_ij로 다음 갱신을 수렴할 때까지 반복합니다(Hunter, 2004의 MM 알고리즘).

p_i ← W_i / Σ_j [ n_ij / (p_i + p_j) ]
그 뒤 전체 p를 정규화 (척도 고정)

매 반복이 가능도를 줄이지 않음이 보장되고, 별도 최적화 라이브러리가 필요 없습니다.
"둘 다 별로"처럼 우열 정보가 없는 표는 점수 추정과 분리해 응답 품질 신호로 따로 봅니다.

BayesElo식 가상 대전: 표가 적은 참가자의 발산 막기#

순수 최대가능도에서는 전승(또는 전패)한 참가자의 점수가 무한대로 발산합니다.
2전 2승 모델이 리더보드 1위에 오르는 식입니다.
그래서 BayesElo(Rémi Coulom)의 가상 대전(virtual games) 사전분포를 넣었습니다.
모든 참가자가 가상의 앵커와 λ판을 이미 치른 것처럼 집계에 더한 뒤 MM 반복을 돌립니다.

왜 보정이 필요했나: 평가 자원의 한계#

사내 평가자는 소수이고 판정할 수 있는 턴 수도 제한적이라, 표본 크기로 문제를 덮을 수 없었습니다.

  • 해가 없을 수 있습니다.
    비교 그래프가 "강하게 연결"될 때만 해가 유한하고(Zermelo, 1929; Ford, 1957), 표가 적으면 이 조건이 쉽게 깨집니다.
  • 극단으로 치우칩니다.
    소표본에서는 점수 차가 과대추정됩니다(Firth, 1993).
  • 분산이 큽니다.
    10표의 승률 표준오차는 √(0.5 × 0.5 / 10) ≈ 0.16으로, 7승 3패와 5승 5패가 구분되지 않습니다.

왜 가상 대전인가: 근거#

① 약한 사전분포입니다.
λ판을 더하면 표준편차 2/√λ인 정규분포에 가까운 사전분포가 됩니다.
λ = 2면 "대부분의 모델은 앵커 상대 승률 6%~94% 사이"라는 약한 가정이라, 순위는 거의 그대로 두고 발산과 극단값만 막습니다.

② 강한 모델은 덜 누릅니다.
꼬리가 두꺼워(log cosh 형태) 표가 충분한 압도적 모델의 점수를 과하게 끌어내리지 않습니다.

③ 축소 추정은 오차를 줄입니다.
공통 기준점 쪽으로 당기면 전체 평균제곱오차가 작아진다는 James-Stein 이래의 결과가 근거입니다.

④ "표 몇 개 분량"으로 읽힙니다.
λ = 2는 실제 표 2개의 무게라, 10표 참가자는 약간 보정되고 100표 참가자는 사실상 영향이 없습니다.

단순화한 예#

상대가 모두 앵커와 같은 강도라고 하면 θ = log(승 / 패)입니다.

참가자실제 전적최대가능도가상 대전 λ=2 적용 (1승 1패 추가)
A1승 0패무한대 (1위)2승 1패 → θ ≈ 0.69
B15승 5패θ ≈ 1.1016승 6패 → θ ≈ 0.98 (1위)

한 판 이긴 A가 B보다 위에 서는 왜곡이 사라지고, B의 점수는 거의 유지됩니다.

다른 방법을 택하지 않은 이유#

  • 최소 표 수로 자르기: 어렵게 모은 표를 버리게 됩니다.
  • 부트스트랩 신뢰구간: 점수를 고치지 못하고, 전승 참가자는 구간도 발산합니다.
  • 완전한 베이지안 추정(MCMC 등): 사내 규모에 비해 무겁고 기존 결과와 대조하기 어렵습니다.

가상 대전은 실제 표와 같은 형식이라 MM 반복을 바꾸지 않고 적용되고, 기존 아레나와 점수를 그대로 대조할 수 있었습니다.
앵커가 척도의 기준점도 겸합니다.

λ = 2를 유지한 이유와 한계#

이론적으로는 모델 간 점수 퍼짐 τ에 맞춰 λ ≈ 4/τ² 로 정합니다.
λ = 2는 τ ≈ 1.4, 즉 "승률이 80:20 정도까지 벌어진다"는 가정이며 WHR의 관례값이기도 합니다.
참가자 3~4명, 쌍당 5~20표 조건으로 각 400회 시뮬레이션했습니다.

실제 모델 간 차이점수 오차가 가장 작은 λλ = 2의 위치
큼 (τ = 1.4)2최적에 가까움
중간 (τ = 0.7)4~8무난
작음 (τ = 0.3)8~16 이상보정이 약해 점수 차를 과장
  • 보정이 없으면(λ = 0) 차이가 크고 표가 적은 조건에서 9~12%가 발산해, 보정 자체는 필수였습니다.
  • 1위 판정 정확도는 λ에 거의 둔감했습니다.
    λ는 점수 차의 크기와 발산 여부를 바꿉니다.
  • λ = 2는 어느 조건에서도 크게 틀리지 않았고, λ = 16처럼 크게 잡으면 차이가 큰 조건에서 오차가 크게 늘었습니다.

값을 바꾸면 기존 아레나와 척도가 끊기고 더 나은 값의 근거도 없어 λ = 2를 유지했습니다.
다만 프롬프트 버전끼리는 차이가 작아(τ 0.3~0.7) 점수 차가 과장될 수 있으므로, 순위와 상대별 승률표를 우선해 읽습니다.
표가 쌓이면 경험적 베이즈나 교차검증으로 λ를 데이터 기반으로 정할 계획입니다.

점수 신뢰도를 정하는 투표 설계#

점수의 정밀도는 산식보다 비교 그래프의 모양에 좌우되므로, 투표 설계를 추정의 일부로 봤습니다.

가장 덜 붙은 쌍부터#

턴마다 한 쌍만 보여주되 지금까지 가장 적게 붙은 쌍을 우선했습니다.
표가 고르게 쌓여 순위 전체가 안정되고(참가자 3명, 30턴이면 10/10/10), 비교 그래프도 끊기지 않습니다.

같은 맥락에서 비교#

다음 턴은 이긴 응답을 맥락으로 이어갑니다.
모든 참가자가 같은 맥락에서 응답하므로 승패가 응답 품질 차이에서 나옵니다.

블라인드는 화면이 아니라 데이터에서#

참가 모델 정보를 화면뿐 아니라 API 응답에서도 숨기고(일반 사용자에게는 참가자 수만 노출), 투표가 끝난 뒤 공개했습니다.

비교 조건 고정#

테스트 생성 시 참가자별 프롬프트 버전과 파라미터를 스냅샷으로 고정했습니다.
Bradley-Terry는 강도가 고정돼 있다고 가정하므로, 도중의 새 배포가 표에 섞이면 안 됩니다.

집계와 읽는 법#

  • 두 단계 리더보드: 모델 단위와 테스트별(모델 × 프롬프트 버전) 리더보드를 따로 냅니다.
  • 상대별 승률표 병행: 이행성(A > B, B > C면 A > C) 가정이 깨지는 곳을 확인합니다.
  • 안정적인 키로 집계: 이름이 바뀌어 표가 쪼개지지 않도록 변하지 않는 모델 식별자로 묶습니다.
  • 표 수 함께 표기: 점수 차가 작고 표가 적으면 순위를 단정하지 않습니다.

결과#

  • 점수 산식이 기존 아레나 구현과 동일함을 확인했습니다(무작위 50회 비교에서 차이 0). 기존 결과와 같은 척도로 이어 볼 수 있습니다.
  • 공용 서버에 반영하고 사내 인원 6명 대상 QA를 진행했습니다.
    이를 활용한 모델 평가는 진행 중입니다.
