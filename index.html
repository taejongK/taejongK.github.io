01 / About

어떤 사람인가

사람들은 어떤 이야기를 좋아할까?
그 답을 찾으려고 AI를 공부했습니다.

스무 살, 사람들이 좋아하는 이야기를 만들고 싶어 영화를 전공했습니다. 그러다 "사람들은 어떤 이야기를 좋아할까?"라는 궁금증이 생겼고, 그 답을 찾기 위해 AI를 공부했습니다.

커리어는 ML 엔지니어로 시작했습니다. 센서 데이터로 사람의 움직임을 측정하고, 이를 바탕으로 학생들의 집중도와 졸음을 탐지하는 프로젝트를 했습니다.

지금은 AI Engineer로, 유저가 캐릭터와 함께 이야기를 만들어 가는 캐릭터 챗봇을 만듭니다. 긴 대화에서도 캐릭터가 흔들리지 않도록 메모리를, 유해한 내용이 나가지 않도록 콘텐츠 세이프티 필터를 설계하고, 팀이 매일 쓰는 사내 업무 도구를 만듭니다.

일하는 방식

  • 실험으로 결정합니다.

    감으로 판단하는 대신 가장 단순한 기준부터 세우고 비교할 수 있는 형태로 만든 뒤에 다음을 정하며, 그 기준으로 아니라고 나오면 이미 만들어 둔 것도 걷어냅니다.

  • 문제는 책상이 아니라 현장에서 찾습니다.

    사용자를 며칠씩 관찰하거나 QA·기획자·언어권별 평가자를 직접 붙여 확인하는 편이, 혼자 판단하고 틀리는 것보다 빠르다고 생각합니다.

  • 기술은 수단이라고 생각합니다.

    무엇을 만들지보다 무엇이 문제인지를 먼저 정의하려 하고, 필요하면 모델 밖의 것도 바꿉니다. 졸음 탐지 모델을 만들면서 순찰 운영 방식 자체를 바꾸자고 제안했던 것이 그런 경우입니다.

  4. (주)버블탭 · 2026.09

    프롬프트 해킹 시도 탐지 대시보드 개발

    Why
    해킹 지표가 9.7%만 판정한 표본 수치였고, 원문이 남지 않아 수법을 볼 수 없었음
    What
    하루 29만 건 → 해킹 의심 10건, 하루 $3.83로 전수 판정
    How
    룰은 후보만 고르고 LLM이 4개 축으로 채점, 운영팀이 근거를 보고 검수함
    전체 내용 펼치기

    문제

    • 기존 일일 지표의 "해킹 성공 N건"은 룰 필터 통과 1,590건 중 9.7%(155건)만 LLM으로 판정한 표본 수치였는데 화면에는 그 구분이 없었음
    • 지표가 집계만 남기고 원문을 버려 어떤 수법이 들어오는지, 누가 반복 시도하는지 볼 수 없었음. 같은 대화방이 이틀 연속 같은 수법으로 성공한 건도 사람이 워크로그를 읽다가 발견

    방법

    • 룰과 LLM의 역할 분리: 하루 29만 건을 전부 LLM으로 판정하면 하루 약 $945라, 룰은 "판정기에 물어볼 가치가 있는가"만 고르는 선별기로 한정. 입력의 공격 문구 50여 개(한/영/일) ∪ 출력의 장면 밖 구조화 나열 점수로 1차 선별
    • 정상 사용 예외는 좁게: 크리에이터가 정의한 명령어(!커뮤 등)의 정상 호출은 제외하되, 토큰을 인용해 공격을 잇는 경우가 숨지 않도록 장식을 벗겼을 때 토큰만 남는 입력만 제외(정밀도 81.9% → 92.3%)
    • LLM 4축 판정: 비공개 설정 노출(D) · 메타 이탈(M) · 대화 맥락(H) · 크리에이터 허용 기능(A)으로 나눠 채점하고 근거 인용을 함께 출력. 초기 조건(D·A만)으로 걸린 31건 중 13건이 한 대화방의 정상 롤플레이임을 확인하고, "유저가 무엇을 했는가"를 보도록 M·H를 조건에 추가
    • 판정 모델 선정: 기존 판정 모델을 정답지로 두고 같은 입력을 다시 물어 비교한 결과, 기준 모델 자체가 temperature 0에서도 비공개 노출 축 일치율 68.4%로 흔들림을 확인. 3회 실행 결과가 완전히 동일하고 약 40배 저렴한 모델로 교체하고, 낮은 정밀도는 사람 검수로 보완하는 구조로 결정
    • 운영팀용 대시보드: 플랫폼별로 건마다 유저 입력·출력·크리에이터 설정 원문과 판정 근거를 문장으로 표시, 확정/아님/보류 검수를 판정 결과와 분리 저장해 재판정해도 사람 라벨이 보존되게 하고 소형 분류 모델 학습 데이터로 추출 가능하게 함. cron 일일 배치 + 슬랙 알림

    결과

    • 하루 응답 290,970건 → 룰 1,355건(0.47%) → 해킹 의심 10건(8개 대화방), 하루 비용 $3.83, 소요 약 3분 (2026.09.03 데이터 기준)
    • 표본이 아닌 전수 판정으로 바꾸고, 운영팀의 검수 부담을 하루 10건대로 줄임

  8. (주)버블탭 · 2026.01 ~ 2026.02

    LLM-as-judge 평가 체계 구축

    Why
    프롬프트나 모델을 바꿔도 좋아졌는지 감으로만 판단했음
    What
    모델 채택·프롬프트 개선의 공통 측정 도구로 사용, 블라인드 QA로 자체 학습 모델 우위 확인(3.45 vs 3.02)
    How
    객관적 제약은 규칙으로, 주관적 품질은 LLM 심사자가 채점하고 사람 평가로 보정함
    전체 내용 펼치기

    문제

    • 프롬프트나 모델을 바꿔도 "좋아진 것 같다" 수준의 감으로만 판단할 수 있었음
    • 캐릭터 챗봇의 출력 품질은 대부분 주관적 요소라 정량화가 어려움
    • 변경 효과를 재현 가능하게 측정할 공통 수단이 없어, 모델 채택·프롬프트 개선의 근거를 댈 수 없음

    방법

    • 캐릭터 챗봇 출력 품질 루브릭을 7개 카테고리 45개 항목(포맷·구조 / 캐릭터 일관성 / 서사·맥락 유지 / 유저 입력 처리 / 표현 품질 / 콘텐츠 안전성 / 시스템·보안)으로 직접 설계. 항목마다 위반 정의·판정 기준·오류 패턴을 명시하고 PASS/FAIL/N/A와 confidence를 JSON으로 강제 출력하도록 judge 프롬프트 작성
    • 시스템 프롬프트의 지시를 독립 검증 가능한 최소 단위로 분해(Atomic Decomposition)한 뒤, 객관적 제약(길이·포맷·언어)은 규칙 기반 이진 판정, 주관적 제약(캐릭터 충실도·톤 일관성)은 LLM 심사자가 5단계 척도로 채점하는 하이브리드 평가 구조 설계
    • 태스크별 전용 루브릭도 함께 설계: 장기기억 요약용 6축 루브릭(DeltaFocus·CompressionEfficiency·StructuralCompliance·DeltaCoverage·CurrentStateClarity·Consistency)과 179건 평가셋을 구축하고 Claude Opus 4.6을 judge 모델로 사용
