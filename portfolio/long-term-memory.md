# 챗봇 장기기억 구조

> 벡터 RAG 기억 검색이 캐릭터 챗봇에서 작동하지 않음을 평가로 규명해 걷어내고, 요약·재압축 구조로 바꾼 뒤, mem0를 참고해 사실·중요도·최근성·관련성을 RRF로 합치는 커스텀 기억 검색을 작은 모델 위에서 설계한 장기기억 아키텍처.

- 기간: 2025.10 ~ 2025.11 (요약 구조 설계) · 2026.05 (요약 모델 자체 서빙 전환) · 2026.09 ~ 2026.10 (커스텀 기억 검색 PoC · 요약 로직 개선)
- 소속: (주)버블탭 AI코어팀
- 역할: 단독 설계·개발
- 사용 기술: Python, Docker, vLLM, OpenRouter, Jinja2, gemma-4-E4B, bge-m3, OpenSearch(BM25), RRF, LLM-as-judge, Rubric Design, Bootstrap

## 문제

장기 대화로 갈수록 캐릭터가 앞서 나온 설정·사건을 놓치고 일관성이 무너졌다. 원인을 추적해보니 여러 겹으로 얽혀 있었다.

- 기존 장기기억은 벡터 기반 RAG 검색에 의존했는데, 캐릭터 챗봇의 유저 입력은 무언가를 직접 묻는 질문형이 아니라 배경 지식처럼 깔려 있어야 하는 형태라 검색 쿼리로 기능하지 못했다.
- 요약 품질 자체를 신뢰할 수 있게 측정할 기준이 없어, 모델·프롬프트를 바꿀 근거가 부족했다.
- 요약 모델을 자체 서빙으로 옮기려 해도, 고빈도 작업이라 지연·비용에 민감한데 이를 검증할 서빙 환경이 없었다.
- 요약·재압축 구조로 바꾼 뒤에도 두 가지가 남았다. 압축이 반복될수록 초반 디테일이 원리적으로 사라지고, 요약에는 호칭·관계처럼 "지금 유효한 값"을 담을 자리가 없어 설정이 앞뒤로 어긋나도 잡을 방법이 없었다.

## 아키텍처 변천: 세 단계

한 번에 지금 구조로 간 게 아니라, 매 단계에서 측정하고 다음 단계로 넘어갔다.

```
1단계  벡터 RAG 기억 검색        유저 입력을 쿼리 삼아 벡터 검색
       (기존 구조, 제거)          → 평가셋으로 측정하니 Recall 약 10%, 입력이 질문형이 아니라 근본적으로 안 맞음
                                   │
                                   ▼
2단계  요약·재압축(SummaryMemory) 5턴마다 새 대화를 요약해 이어 붙이고 프롬프트에 주입
       (2025.10–11 설계)          길이 상한을 넘으면 기존 요약을 다시 압축, 장기 세션에서도 토큰 낭비 없이 유지
                                   │
                                   ▼
3단계  역할 분담형 기억 (PoC)     요약을 대체하지 않고 역할을 나눔
       (2026.09–10, mem0 분석)    서사(기존 요약) · 상태(항목마다 값 하나, 덮어씀) · 사건(쌓아두고 검색)
                                   사건 검색 = 사실·중요도 · 최근성 · 관련성(유저 입력/직전 출력 × 코사인/BM25)을 RRF로 합침
                                   → 추출 recall 58.9% → 74.4%, 검색 Precision@3 평균 48% (51~150턴 68%)
```

## 기술 의사결정

### 벡터 RAG를 개선이 아니라 제거로 판단한 이유

검색 정제 레이어(리랭커·쿼리 재작성 등)를 얹는 방안도 있었다. 하지만 문제의 근원이 "검색이 정교하지 않다"가 아니라 "유저 입력 자체가 검색 쿼리로 기능할 수 없는 형태"라는 걸 평가로 확인한 뒤로는, 레이어를 더 얹는 게 비용 대비 실익이 없다고 판단했다. 구조 자체를 요약 기반으로 바꾸는 쪽을 택한 이유다.

### 왜 곧장 검색으로 가지 않고 요약을 먼저 거쳤나

캐릭터의 정적인 설정(이름·성격·배경)은 이미 시스템 프롬프트가 담당한다. 장기기억이 실제로 추적해야 하는 건 "무엇이 바뀌었는가"라는 델타뿐이다. 그래서 1차로는 가장 단순한 안, 즉 대화를 요약해 매 턴 주입하는 구조를 먼저 세우고 측정했다. 요약 프롬프트도 그 기준으로 다듬었다: 정적 배경은 제외하고 감정·시간·위치·아이템·행동 5개 델타 도메인만 체크하도록, 그리고 "마지막 문장은 현재 상태로 종료"하도록 규칙을 넣었다. 이 단계에서 평가자 10인의 사람 평가와 상관관계 0.85로 캘리브레이션한 6축 루브릭을 함께 만들어, 이후 모든 변경을 이 잣대로 검증했다.

### 외부 API 대신 자체 서빙을 택한 근거

요약은 고빈도 작업이라 지연과 비용이 그대로 서비스 체감으로 이어진다. 그래서 모델을 바꾸기 전에 서빙 방식부터 실측해 비교했다. 품질(6축 루브릭), 평균·최대 응답 지연, 건당 비용, 고부하 성공률의 네 축이다.

- 품질은 자체 서빙 쪽이 기존 외부 API 대비 확실히 높았고, 양자화 방식 간 차이는 미미해 **정밀도를 낮춰도 품질이 깨지지 않는다**는 것을 확인했다
- 평균 지연은 외부 API가 빨랐지만 **최대 응답 지연의 편차가 컸다.** 자체 서빙은 평균은 느려도 최대치가 안정적이라, 매 턴 도는 작업에는 이쪽이 맞다고 판단했다
- 고부하 구간에서 외부 API는 실패율이 급증한 반면 자체 서빙은 전 구간 성공했고, 부하를 올려가며 **최적 동시 요청 수**를 따로 도출했다
- 건당 비용은 자체 서빙이 수 배 저렴했다

전환은 별도 인프라를 세우지 않고 **기존 자체 서빙 환경에 얹는 방식**으로 했다. 요약이라는 부가 호출을 이미 돌아가는 서빙에 흡수시켜, 추가 API 비용이 들지 않게 한 것이다.

### mem0에서 가져온 것과 버린 것

mem0 코어 SDK의 로직을 분석한 뒤, **"사건을 문장으로 쌓아두고 필요할 때 검색해 꺼낸다"는 뼈대만** 가져왔다. 압축 소실을 정면으로 해결하는 부분이다. 그대로 쓰지 않은 이유는 셋이다.

- mem0는 기존 기억을 고치지 않고 쌓기만 한다. 모순된 기억이 그대로 공존하고, 무엇이 최신인지 판단하는 책임이 쓰는 쪽으로 넘어온다.
- 엔티티 추출 등 일부 구성요소가 영어 전용이라 4개 언어권 서비스에 쓸 수 없다.
- 사건 목록만으로는 롤플레이의 관계와 분위기가 담기지 않는다.

그래서 요약을 대체하지 않고 역할을 나눴다. **서사**(기존 요약)는 관계와 감정의 흐름을, **상태**는 호칭·말투·관계·장소·약속처럼 지금 유효한 값을 항목마다 하나만 두고 덮어써서 모순이 공존할 수 없게, **사건**은 매 턴 일어난 일을 쌓아두고 관련된 것만 검색해 넣는다. 핵심은 압축돼 사라진 걸 되살리는 게 아니라 **애초에 압축 대상에서 사실을 빼는 것**이다. 디테일 소실은 사건이, 설정 모순은 상태가 맡는다.

### 작은 모델이라는 제약을 전제로 실험

부가 작업은 작은 모델로 돌려야 하는 GPU 자원 제약이 있어, 추출 모델을 4B급 gemma-4-E4B로 고정하고 그 안에서 개선했다. mem0를 그대로 재현한 v1을 기준선으로 두고 버전마다 한 가지씩만 바꿨다.

- 추출 단위를 줄이자(턴당 1개) 검색 순위는 좋아졌지만 recall이 58% → 49%로 떨어져 약속·호칭이 특히 빠졌다. 반대로 작은 모델은 "저장할 것 없음"을 거의 판단하지 못해 상한이 없으면 사소한 기록으로 칸을 채웠다.
- 그래서 추출 범주를 판정 기준과 같은 6개 유형(호칭·이름 · 사실·설정 · 사건 · 약속·금기 · 관계·감정 변화 · 선호)에 맞추고 턴당 최대 3개로 상한을 두었다. precision은 90% 수준을 유지하면서 recall이 74.4%로 올랐다. 대가로 저장 항목 수가 2.9배가 됐다.
- 검색 개선은 질의보다 **저장되는 항목의 형태**에서 나왔다. 질의 재작성과 이름 점수는 효과가 없어 뺐다.

### 검색 질의에 직전 캐릭터 출력을 넣은 이유 (RRF)

1단계에서 확인한 "유저 발화는 검색 질의로 약하다"는 진단을 그대로 이어받았다. 유저 입력과 직전 캐릭터 출력으로 각각 검색한 뒤 점수 대신 순위만 합치는 RRF를 적용했다. 직전 출력으로 찾은 1위의 관련률(43%)이 유저 입력 쪽(36%)보다 높게 측정돼, 가중치를 0.3 : 0.7로 직전 출력에 두고 k는 10으로 정했다. 유저 입력만 검색할 때 대비 Precision@3이 34.1% → 38.8%로 유의하게 올랐다.

### 리랭커를 시도하고 보류한 이유

상위 10개 안의 관련 기억을 1~3위로 올리기만 해도 Precision@3은 82.1%까지 가능한데 실제는 38.8%였다. 후보는 잘 모으는데 순서를 못 정하는 문제다. 지금 점수 4개(의미·단어 × 유저 입력·직전 출력)를 비선형으로 섞어도 구분력이 AUC 0.57에서 멈춰, 질의와 기억을 함께 읽는 범용 리랭커(bge-reranker-v2-m3)를 시험했다.

결과는 유의하지 않았다(Precision@3 +2.0%p, Precision@1은 오히려 하락). 원인은 두 가지로 봤다. 범용 리랭커는 "질문 → 답이 든 문서"를 고르도록 학습돼 롤플레이 대사와 기억을 관련·무관 모두 "관련 없음"으로 본다. 그리고 직전 출력이 길어 쌍의 70%가 입력 한도(1,024토큰)에서 잘려 가장 최근 장면이 사라진다. 필요한 건 "다음 응답에 쓰일 기억"을 고르는 판단이라, 범용 모델로는 맞지 않는다고 판단해 보류했다.

### 최종: 신호를 늘려 RRF로 합친 커스텀 검색

순서를 범용 모델에 맡기는 대신, 순서를 정하는 데 쓸 신호를 늘렸다. mem0의 구성을 그대로 쓰지 않고 직접 짰다. 작은 모델(gemma-4-E4B)로 대화에서 사실과 중요도를 추출하고, 턴 수 기준 최근성과 유저 입력·직전 캐릭터 출력 각각의 코사인 유사도·BM25 관련성을 구해 이 순위들을 RRF로 합쳤다. 점수 스케일이 서로 다른 신호를 정규화 없이 섞을 수 있다는 점이 RRF를 유지한 이유다.

Precision@3은 평균 48%였고, 턴 구간별로 1~25턴 30%, 26~50턴 42%, 51~150턴 68%였다. 대화가 길수록 쌓인 사실이 많고 요약이 잃는 디테일도 많은 구간이라, 검색 기억이 필요한 곳에서 가장 잘 작동한다.

### 평가 체계를 먼저 세움

한국어 실서비스 대화 21개(1~50턴, 이후 최대 150턴까지 확장)로 추출(precision · recall)과 검색(Precision@k · DCG@3) 두 축의 평가셋을 만들었다. 상위 모델이 이진으로 판정하되 일부만 맞으면 오답으로 쳤고, 버전 간 차이는 짝지은 질의 부트스트랩(2,000회)으로 유의성을 검정했다. 순서 반영 지표는 저장소 전체의 관련 수를 알 수 없어 nDCG 대신 DCG@3을 썼다.

### 요약 로직 개선: 모델 교체 리스크를 로직으로 메우기

GPU 장비 부족으로 요약 모델을 더 작은 모델로 바꿔야 할 수 있어, 품질 차이와 로직으로 메울 수 있는지를 먼저 검증했다. 요약할 때 직전 요약을 입력에 이어 넣어 앞 맥락을 잇고(temperature 0), 작은 모델이 자주 틀리는 부분(직전 요약 제목 베끼기 · 행위 주체 반전 · 약속 누락)을 겨냥한 지시를 추가했다. 21개 대화 179청크를 상위 모델이 쌍으로 비교 판정했다.

- 출시 후 유저 설문에서 버블챗·팅글의 장점으로 '장기 기억'이 꼽힘
- 작은 모델 + 개선 로직이 현행 모델 + 현행 로직보다도 우세(107 : 65)해, 모델 교체 리스크를 로직으로 메울 수 있음을 확인. 현행 모델을 유지한 채 입력·파라미터·프롬프트만 바꾸는 변경안을 문서화해 개발팀에 적용 요청
- 커스텀 기억 검색은 실서비스 적용 전 PoC 단계. 남은 과제는 짧은 대화(1~25턴, 30%) 구간의 정확도
