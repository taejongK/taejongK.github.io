# 챗봇 장기기억 구조

> 벡터 RAG 기억 검색이 캐릭터 챗봇에서 작동하지 않음을 평가로 규명해 걷어내고, 요약·재압축을 거쳐 자체 GPU 서빙 인덱스 기반 검색으로 다시 설계한 장기기억 아키텍처.

- 기간: 2025.10 ~ 2025.11 (구조 설계) · 2026.05 (요약 모델 자체 서빙 전환) · 2026.09 (인덱스 기반 검색 전환)
- 소속: (주)버블탭 AI코어팀
- 역할: 단독 설계·개발
- 사용 기술: Python, Docker, vLLM, OpenRouter, Jinja2, LLM-as-judge, Rubric Design

## 문제

장기 대화로 갈수록 캐릭터가 앞서 나온 설정·사건을 놓치고 일관성이 무너졌다. 원인을 추적해보니 세 겹으로 얽혀 있었다.

- 기존 장기기억은 벡터 기반 RAG 검색에 의존했는데, 캐릭터 챗봇의 유저 입력은 무언가를 직접 묻는 질문형이 아니라 배경 지식처럼 깔려 있어야 하는 형태라 검색 쿼리로 기능하지 못했다.
- 요약 품질 자체를 신뢰할 수 있게 측정할 기준이 없어, 모델·프롬프트를 바꿀 근거가 부족했다.
- 요약 모델을 자체 서빙으로 옮기려 해도, 매 턴 실행되는 고빈도 작업이라 지연·비용에 민감한데 이를 검증할 서빙 환경이 없었다.

## 아키텍처 변천: 세 단계

한 번에 지금 구조로 간 게 아니라, 매 단계에서 측정하고 다음 단계로 넘어갔다.

```
1단계  벡터 RAG 기억 검색        유저 입력을 쿼리 삼아 벡터 검색
       (기존 구조, 제거)          → 평가셋으로 측정하니 Recall 약 10%, 입력이 질문형이 아니라 근본적으로 안 맞음
                                   │
                                   ▼
2단계  요약·재압축(SummaryMemory) 매 10턴마다 누적 대화를 자동 요약해 프롬프트에 주입
       (2025.10–11 설계)          6,000자를 넘으면 기존 요약을 다시 압축, 장기 세션에서도 토큰 낭비 없이 유지
                                   │
                                   ▼
3단계  인덱스 기반 메모리 검색    요약에 더해, 매 턴 인덱스 구성요소를 추출해 인덱스에 적재
       (2026.09 재설계)           같은 모델이 필요한 순간 인덱스를 조회해 청크만 선택적으로 검색
                                   → Precision@5 90.2% / Recall@5 84.3%
```

## 기술 의사결정

### 벡터 RAG를 개선이 아니라 제거로 판단한 이유

검색 정제 레이어(리랭커·쿼리 재작성 등)를 얹는 방안도 있었다. 하지만 문제의 근원이 "검색이 정교하지 않다"가 아니라 "유저 입력 자체가 검색 쿼리로 기능할 수 없는 형태"라는 걸 평가로 확인한 뒤로는, 레이어를 더 얹는 게 비용 대비 실익이 없다고 판단했다. 구조 자체를 요약 기반으로 바꾸는 쪽을 택한 이유다.

### 왜 곧장 인덱스 검색으로 안 가고 요약을 먼저 거쳤나

캐릭터의 정적인 설정(이름·성격·배경)은 이미 시스템 프롬프트가 담당한다. 장기기억이 실제로 추적해야 하는 건 "무엇이 바뀌었는가"라는 델타뿐이다. 그래서 1차로는 가장 단순한 안, 즉 누적 대화를 통째로 요약해 매 턴 주입하는 구조를 먼저 세우고 측정했다. 요약 프롬프트도 그 기준으로 다듬었다: 정적 배경은 제외하고 감정·시간·위치·아이템·행동 5개 델타 도메인만 체크하도록, 그리고 "마지막 문장은 현재 상태로 종료"하도록 규칙을 넣었다. 이 단계에서 평가자 10인의 사람 평가와 상관관계 0.85로 캘리브레이션한 6축 루브릭을 함께 만들어, 이후 모든 변경을 이 잣대로 검증했다.

### 외부 API 대신 자체 서빙을 택한 근거

요약은 매 턴 도는 고빈도 작업이라 지연과 비용이 그대로 서비스 체감으로 이어진다. 그래서 모델을 바꾸기 전에 서빙 방식부터 실측해 비교했다. 품질(6축 루브릭), 평균·최대 응답 지연, 건당 비용, 고부하 성공률의 네 축이다.

- 품질은 자체 서빙 쪽이 기존 외부 API 대비 확실히 높았고, 양자화 방식 간 차이는 미미해 **정밀도를 낮춰도 품질이 깨지지 않는다**는 것을 확인했다
- 평균 지연은 외부 API가 빨랐지만 **최대 응답 지연의 편차가 컸다.** 자체 서빙은 평균은 느려도 최대치가 안정적이라, 매 턴 도는 작업에는 이쪽이 맞다고 판단했다
- 고부하 구간에서 외부 API는 실패율이 급증한 반면 자체 서빙은 전 구간 성공했고, 부하를 올려가며 **최적 동시 요청 수**를 따로 도출했다
- 건당 비용은 자체 서빙이 수 배 저렴했다

전환은 별도 인프라를 세우지 않고 **기존 자체 서빙 환경에 얹는 방식**으로 했다. 요약·인덱스 추출이라는 부가 호출을 이미 돌아가는 서빙에 흡수시켜, 기능을 늘리면서도 추가 API 비용이 들지 않게 한 것이다.

### 같은 모델에 요약과 인덱스 추출을 함께 태운 구조

3단계로 넘어가면서 매 턴 해야 할 일이 늘었다: 대화 요약과 인덱스 구성요소 추출 두 가지다. 이 둘을 별도 모델·별도 호출로 나누지 않고 같은 자체 서빙 모델이 함께 처리하도록 묶었다. 턴마다 발생하는 부가 LLM 호출을 하나의 서빙 인프라로 흡수시켜, 인덱스 기능을 얹는다고 매 턴 호출 수가 배로 늘지 않게 한 것이다. 검색이 필요한 순간에도 같은 모델이 인덱스를 조회해 필요한 청크만 선택적으로 가져온다. 전체 인덱스를 매번 프롬프트에 욱여넣지 않는다.

### 평가셋을 상위 모델 라벨링 + 육안 샘플 검증으로 구축

검색 성능(Precision@5 / Recall@5)을 측정하려면 정답 라벨이 있는 평가셋이 필요했다. 실서비스 대화 1,000건을 임베딩 기반 필터링으로 추린 뒤 상위 모델로 자동 라벨링하되, 그 라벨을 그대로 믿지 않고 샘플을 육안으로 검증했다. 라벨링 프롬프트 자체를 이 검증 결과로 반복 교정한 뒤에야 정확도를 확보했다. 콘텐츠 필터 프로젝트에서 라벨 오류를 전수 교정해야 했던 것과 같은 맥락으로, 자동 라벨링 결과를 곧바로 정답으로 쓰지 않는다는 원칙을 여기서도 지켰다.

## 결과

| 지표 | 이전 | 이후 |
|---|---|---|
| 기억 검색 Recall (동일 평가셋) | 벡터 RAG 약 10% | 인덱스 기반 Recall@5 84.3% (Precision@5 90.2%) |
| 요약 품질 6축 루브릭 평균 | 3.55 | 3.99 |

| 요약·인덱스 추출 비용 | 외부 API 종량 과금 (월 약 ₩1,710,000 규모 · 프로덕션 실측 일 5만 건 기준) | 자체 GPU 서빙 흡수, 추가 API 비용 ₩0 |

- 요약·재압축을 거쳐 인덱스 기반 검색까지 전환해 장기 세션 캐릭터 일관성 및 스토리 연속성 개선, 내부 QA 장기기억 품질 평가 2/5 → 4/5 향상
- 출시 후 유저 설문에서 버블챗·팅글의 장점으로 '장기 기억'이 꼽힘
- 자체 서빙 전환으로 기존 인프라가 요약·인덱스 추출 비용을 흡수, 추가 API 비용 없이 기능을 확장
