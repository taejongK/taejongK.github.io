# 챗봇 장기기억 구조

> 캐릭터 챗봇에서 벡터 RAG 기억 검색이 작동하지 않음을 평가로 확인해 요약·재압축 구조로 바꾸고, mem0를 참고해 작은 모델 위에서 RRF 기반 커스텀 기억 검색을 설계했습니다.

- 기간: 2025.10 ~ 2025.11 (요약 구조 설계) · 2026.05 (요약 모델 자체 서빙 전환) · 2026.09 ~ 2026.10 (커스텀 기억 검색 설계·적용 · 요약 로직 개선)
- 소속: (주)버블탭 AI코어팀
- 역할: 단독 설계·개발
- 사용 기술: Python, Docker, vLLM, OpenRouter, Jinja2, gemma-4-E4B, bge-m3, OpenSearch(BM25), RRF, LLM-as-judge, Rubric Design, Bootstrap

## 문제

대화가 길어질수록 캐릭터가 앞선 설정·사건을 놓치고 일관성이 무너졌습니다. 원인은 여러 겹이었습니다.

- 기존 장기기억은 벡터 RAG 검색에 의존했지만, 캐릭터 챗봇의 유저 입력은 질문형이 아니어서 검색 쿼리로 기능하지 못했습니다.
- 요약 품질을 측정할 기준이 없어 모델·프롬프트를 바꿀 근거가 부족했습니다.
- 요약 모델의 자체 서빙 전환을 검증할 환경이 없었습니다.
- 요약·재압축 구조에서도 압축이 반복되면 초반 디테일이 사라지고, 호칭·관계처럼 "지금 유효한 값"을 담을 자리가 없었습니다.

## 아키텍처 변천: 세 단계

매 단계에서 측정한 뒤 다음 단계로 넘어갔습니다.

```
1단계  벡터 RAG 기억 검색        유저 입력을 쿼리 삼아 벡터 검색
       (기존 구조, 제거)          → 평가셋으로 측정하니 Recall 약 10%, 입력이 질문형이 아니라 근본적으로 안 맞음
                                   │
                                   ▼
2단계  요약·재압축(SummaryMemory) 5턴마다 새 대화를 요약해 이어 붙이고 프롬프트에 주입
       (2025.10–11 설계)          길이 상한을 넘으면 기존 요약을 다시 압축, 장기 세션에서도 토큰 낭비 없이 유지
                                   │
                                   ▼
3단계  역할 분담형 기억 (적용)    요약을 대체하지 않고 역할을 나눔
       (2026.09–10, mem0 분석)    서사(기존 요약) · 상태(항목마다 값 하나, 덮어씀) · 사건(쌓아두고 검색)
                                   사건 검색 = 사실·중요도 · 최근성 · 관련성(유저 입력/직전 출력 × 코사인/BM25)을 RRF로 합침
                                   → 추출 recall 58.9% → 74.4%, 검색 Precision@3 평균 48% (51~150턴 68%)
```

## 기술 의사결정

### 벡터 RAG를 개선이 아니라 제거로 판단한 이유

리랭커·쿼리 재작성 같은 정제 레이어도 검토했지만, 평가해 보니 근원은 "유저 입력이 쿼리로 기능할 수 없는 형태"였습니다. 레이어를 얹는 실익이 없다고 보고 요약 기반 구조로 바꿨습니다.

### 검색보다 요약을 먼저 거친 이유

캐릭터의 정적 설정(이름·성격·배경)은 시스템 프롬프트가 담당하므로, 장기기억은 "무엇이 바뀌었는가"라는 델타만 추적하면 됩니다. 그래서 가장 단순한 안인 매 턴 요약 주입을 먼저 세우고 측정했습니다. 요약 프롬프트는 정적 배경을 빼고 감정·시간·위치·아이템·행동 5개 델타 도메인만 체크하며, "마지막 문장은 현재 상태로 종료"하도록 했습니다. 함께 평가자 10인의 사람 평가와 상관관계 0.85로 캘리브레이션한 6축 루브릭을 만들어 이후 모든 변경을 검증했습니다.

### 외부 API 대신 자체 서빙을 택한 근거

요약은 고빈도 작업이라 품질(6축 루브릭), 평균·최대 응답 지연, 건당 비용, 고부하 성공률 네 축으로 실측 비교했습니다.

- 품질은 자체 서빙이 확실히 높았고, 양자화 방식 간 차이가 미미해 **정밀도를 낮춰도 품질이 유지**됨을 확인했습니다
- 평균 지연은 외부 API가 빨랐지만 **최대 지연 편차가 컸습니다.** 매 턴 도는 작업에는 최대치가 안정적인 자체 서빙이 맞다고 판단했습니다
- 고부하에서 외부 API는 실패율이 급증했지만 자체 서빙은 전 구간 성공했습니다
- 건당 비용은 자체 서빙이 수 배 저렴했습니다

별도 인프라 없이 **기존 자체 서빙 환경에 얹어** 추가 API 비용이 들지 않게 했습니다.

### mem0에서 가져온 것과 버린 것

mem0 코어 SDK를 분석해 **"사건을 문장으로 쌓아두고 필요할 때 검색한다"는 뼈대만** 가져왔습니다. 압축 소실을 해결하는 부분입니다. 그대로 쓰지 않은 이유는 셋입니다.

- 기존 기억을 고치지 않고 쌓기만 해서 모순된 기억이 공존합니다.
- 엔티티 추출 등 일부 구성요소가 영어 전용이라 4개 언어권 서비스에 쓸 수 없습니다.
- 사건 목록만으로는 롤플레이의 관계와 분위기가 담기지 않습니다.

그래서 역할을 나눴습니다. **서사**(기존 요약)는 관계와 감정의 흐름을, **상태**는 호칭·말투·관계·장소·약속처럼 지금 유효한 값을 항목마다 하나만 두고 덮어쓰며, **사건**은 매 턴 일어난 일을 쌓아두고 관련된 것만 검색해 넣습니다. 핵심은 **애초에 압축 대상에서 사실을 빼는 것**입니다. 디테일 소실은 사건이, 설정 모순은 상태가 맡습니다.

### 작은 모델이라는 제약을 전제로 실험

GPU 자원 제약으로 추출 모델을 4B급 gemma-4-E4B로 고정했습니다. mem0를 재현한 v1을 기준선으로, 버전마다 한 가지씩만 바꿨습니다.

- 추출 단위를 턴당 1개로 줄이자 검색 순위는 좋아졌지만 recall이 58% → 49%로 떨어졌습니다. 반대로 상한이 없으면 작은 모델이 사소한 기록으로 칸을 채웠습니다.
- 추출 범주를 판정 기준과 같은 6개 유형(호칭·이름 · 사실·설정 · 사건 · 약속·금기 · 관계·감정 변화 · 선호)으로 맞추고 턴당 최대 3개로 제한했습니다. precision 90% 수준을 유지하며 recall이 74.4%로 올랐고, 저장 항목 수는 2.9배가 됐습니다.
- 검색 개선은 질의보다 **저장 항목의 형태**에서 나왔습니다. 질의 재작성과 이름 점수는 효과가 없어 뺐습니다.

### 검색 질의에 직전 캐릭터 출력을 넣은 이유 (RRF)

"유저 발화는 검색 질의로 약하다"는 1단계 진단을 이어받아, 유저 입력과 직전 캐릭터 출력으로 각각 검색한 뒤 순위만 합치는 RRF를 적용했습니다. 직전 출력 쪽 1위 관련률(43%)이 유저 입력 쪽(36%)보다 높아 가중치를 0.3 : 0.7로 직전 출력에 두고 k는 10으로 정했습니다. Precision@3이 34.1% → 38.8%로 유의하게 올랐습니다.

### 리랭커를 시도하고 보류한 이유

상위 10개 안의 관련 기억을 1~3위로만 올려도 Precision@3은 82.1%인데 실제는 38.8%로, 순서를 못 정하는 문제였습니다. 점수 4개(의미·단어 × 유저 입력·직전 출력)를 비선형으로 섞어도 AUC 0.57에 머물러 범용 리랭커(bge-reranker-v2-m3)를 시험했습니다.

결과는 유의하지 않았습니다(Precision@3 +2.0%p, Precision@1은 하락). 범용 리랭커는 "질문 → 답이 든 문서"를 고르도록 학습돼 롤플레이 대사와 기억을 모두 "관련 없음"으로 보고, 쌍의 70%가 입력 한도(1,024토큰)에서 잘려 최근 장면이 사라졌습니다. "다음 응답에 쓰일 기억"을 고르는 판단에는 맞지 않아 보류했습니다.

### 최종: 신호를 늘려 RRF로 합친 커스텀 검색

순서를 범용 모델에 맡기는 대신 신호를 늘렸습니다. gemma-4-E4B로 사실과 중요도를 추출하고, 턴 수 기준 최근성과 유저 입력·직전 출력 각각의 코사인 유사도·BM25 관련성을 구해 RRF로 합쳤습니다. 스케일이 다른 신호를 정규화 없이 섞을 수 있어 RRF를 유지했습니다.

Precision@3은 평균 48%, 구간별로 1~25턴 30%, 26~50턴 42%, 51~150턴 68%였습니다. 요약이 잃는 디테일이 많은 긴 대화에서 가장 잘 작동합니다.

### 평가 체계를 먼저 세움

한국어 실서비스 대화 21개(1~50턴, 이후 최대 150턴까지 확장)로 추출(precision · recall)과 검색(Precision@k · DCG@3) 평가셋을 만들었습니다. 상위 모델이 이진 판정하되 일부만 맞으면 오답으로 쳤고, 버전 간 차이는 짝지은 질의 부트스트랩(2,000회)으로 검정했습니다. 저장소 전체의 관련 수를 알 수 없어 nDCG 대신 DCG@3을 썼습니다.

### 요약 로직 개선: 모델 교체 리스크를 로직으로 메우기

GPU 장비 부족으로 요약 모델을 더 작게 바꿔야 할 수 있어, 로직으로 품질 차이를 메울 수 있는지 먼저 검증했습니다. 직전 요약을 입력에 이어 넣고(temperature 0), 작은 모델이 자주 틀리는 부분(직전 요약 제목 베끼기 · 행위 주체 반전 · 약속 누락)을 겨냥한 지시를 추가했습니다. 21개 대화 179청크를 상위 모델이 쌍으로 비교 판정했습니다.

- 커스텀 기억 검색은 서비스에 적용했습니다. 남은 과제는 짧은 대화(1~25턴, 30%) 구간의 정확도입니다
