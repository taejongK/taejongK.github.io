# 이미지 검열 시스템

> 규정은 질문으로 옮기고, 모델은 확률만 내고, 라벨은 서버가 정합니다. 판정 모델을 직접 서빙하고 운영팀 검수 보조 도구까지 만들었습니다.

- 기간: 2026.10 ~ 2026.11
- 소속: (주)버블탭 AI코어팀
- 역할: 단독 기획·판정 구조 설계·모델 서빙·검수 도구 개발·검증
- 사용 기술: clef-flash(Qwen3.5-9B), FastAPI, PyTorch, transformers, flash-linear-attention, causal-conv1d, CUDA, Docker, SQLite, Jinja2

## 문제

- **대화 중 이미지 전송**: 업로드 직후 1초 이내에 내부 검열 기준으로 판정해야 했습니다.
- **공개 캐릭터 이미지 검수**: 운영팀은 썸네일·멀티이미지를 한 장씩 검수합니다. 판정 보조가 있었지만 어드민 밖에 있어, 어드민에서 같은 이미지를 다시 찾아 확인해야 했습니다.

운영팀 킥오프에서 나온 불편 8개의 핵심은 **"일을 두 번 한다"** 였습니다. 그래서 목표를 더 좋은 모델이 아니라 **판정은 초벌, 확정은 운영자인 검수 보조**로 잡았고, 자동 차단은 하지 않습니다.

## 판정 구조

**규정과 질문**, **확률과 라벨**, **분류와 사유**를 분리했습니다.

```
규정 문서 (판정 기준의 원본)
    │  질문·선택지 문장으로 옮김
    ▼
[1단계 분류]  이미지 1장 → 요청 1번, 질문 3개
              safe 여부 · 성인 수위 · 실사 여부의 확률
    │  확률을 저장
    ▼
서버가 기준값으로 라벨 계산
    실사 ≥ 기준값            → block
    아니면 safe ≥ 기준값      → safe   (대부분 여기서 끝)
    아니면 adult ≥ 기준값     → adult
    아니면                    → block
    │
    ▼  adult · block 만
[2단계 사유]  판정된 라벨의 사유 태그만 yes / no 로 한 요청에 묶어 질문
              (질문 20개 한 요청 0.6~0.9초)
    │
    ▼
검수 화면: 이미지 + 라벨 + 점수 + 미리 체크된 사유 → 운영자가 확정
    │  운영자가 고친 라벨·사유
    ▼
정답 데이터로 축적
```

### 생성 모델이 아니라 결정 모델

Cloudflare의 결정(분류) 모델 clef-flash를 골랐습니다. Qwen3.5-9B에 선택지 확률을 내는 head가 붙어 있어 **글을 생성하지 않고 질문마다 확률을 돌려줍니다.** 출력 형식이 흔들리거나 근거 문장을 파싱할 일이 없습니다.

채팅 이미지 평가셋 191장에서 gemma-4-E4B-it와 비교해 채택했습니다.

| 모델 | 정확도 | 탐지율 | 오탐률 | 장당 시간 |
|---|---|---|---|---|
| gemma-4-E4B-it | 0.937 | 0.940 | 0.064 | 0.63초 |
| **clef-flash** | **0.984** | **0.960** | **0.007** | **0.23초** |

질문 형식은 예/아니오보다 **정상 기준을 선택지로 직접 주는 형식**이 정상 이미지 점수를 덜 부풀렸습니다.

### 규정 문서가 판정 기준의 원본

Opus가 기준 문서만 보고 사람 라벨 1,000장을 재현하도록 **판정 → 사람 검수 → 불일치 반영**을 6번 반복해 판정 기준 v6를 만들었습니다. 사람 라벨과의 3분류 일치율은 0.975, 이 기준에서 clef-flash 정확도는 0.939였습니다.

캐릭터 이미지는 서비스(버블챗·팅글) × 종류(썸네일·멀티이미지)마다 규정이 달라 판정 규칙을 4가지로 나눴습니다. 모호한 경계는 예시 이미지와 함께 운영팀 결정을 받았습니다.

### 확률 저장, 라벨은 읽을 때 계산

확률을 저장하고 라벨은 화면에 보일 때 계산하므로, 기준값을 바꿔도 **모델을 다시 부르지 않습니다.** 기준값 조절 페이지에서는 슬라이더를 움직이면 라벨별 장수, 바뀌는 장수, 운영자 검토와의 일치율을 바로 보여줍니다.

### 판정된 라벨의 사유만 질문

태그 전부를 물으면 adult 이미지에 block 사유가 붙었습니다. **질문 범위**의 문제여서 adult면 adult 태그와 미성년 외형만, block이면 block 태그만 묻도록 제한했습니다.

adult 기준값을 아주 조금 못 넘어 block으로 떨어졌지만 block 사유는 없는 이미지도 있었습니다. "실사가 아니고 기준값을 넘는 block 사유도 없으면 adult" 규칙을 넣으면서, 저장된 14,098장을 재계산해 영향 범위(9장)를 먼저 확인했습니다.

사유 질문을 서비스별 템플릿 파일로 분리할 때는 전후 요청 본문 8가지(질문 67개)가 **바이트 단위로 같음**을 확인해 재판정 없이 반영했습니다.

## clef-flash 직접 서빙

### 맞지 않던 공식 서빙 경로

공식 서빙 경로는 H200급 GPU 기준의 SGLang 전용 이미지뿐이었고, vLLM은 글 생성용이라 확률 head를 실행하지 못했습니다. 그래서 동봉된 추론 코드를 **FastAPI로 감싸 SGLang과 같은 요청·응답 형식**으로 열어, 나중에 SGLang으로 바꿔도 호출 코드를 그대로 쓸 수 있게 했습니다. API 키 인증, 입력 검증, GPU 1장 순차 처리와 대기열 상한(초과 시 429)도 넣었습니다.

### 41초를 1.8초로

처음에는 1.5만 토큰 입력이 41초 걸렸습니다. Qwen3.5는 32개 층 중 24개가 linear attention인데, 빠른 구현이 별도 라이브러리에 있고 없으면 순수 torch 구현으로 대신합니다.

| 입력 | 기본 | + flash-linear-attention | + causal-conv1d |
|---|---|---|---|
| 약 15,300 토큰 | 41,437 ms | 1,898 ms | **1,780 ms** |
| 이미지 1장 (1024×768) | 319 ms | 203 ms | **202 ms** |

RTX 4090, 1건씩 5회 측정한 중앙값입니다. causal-conv1d는 torch·CUDA 버전을 고정해 소스 컴파일했습니다.

### 이식과 이중화

모델 리비전을 고정하고 여러 GPU 아키텍처용 커널을 함께 빌드한 Docker 이미지로 A100에 옮겼습니다. 같은 모델을 세 곳(사내 A100 → 4090 → OpenRouter)에 두고, 30초마다 상태를 확인해 켜진 곳 중 1순위부터 호출하며 실패하면 다음 순위로 넘깁니다.

서버별 확률 차이는 4090이 0.01 이내, OpenRouter가 0.01~0.04였고, 판정마다 어느 서버가 냈는지 저장합니다.

## 검수 보조 도구

![위험도순 정렬, 판정 집계·검토 진행률·어드민 상태를 한 표에 둔 캐릭터 목록](character-list.jpeg)

- 운영자에게 익숙한 어드민의 캐릭터 목록 · 이미지 목록 구조를 따르고 어드민 바로가기를 붙였습니다.
- 10분마다 최근 공개 캐릭터를 미리 분류해, 운영자가 열 때 이미 판정이 끝나 있습니다.
- **스캔 범위 확장**: 최초 공개일 기준이라 공개 후 교체·추가된 이미지가 빠지고 있었습니다. DB 동작(썸네일은 새 행, 멀티이미지는 같은 행 수정)을 확인하고 이미지 수정 시각 기준 스캔을 추가해 첫 스캔에서 1,009장을 새로 분류했습니다.
- **프롬프트 속 외부 이미지**: 캐릭터 텍스트에 적힌 외부 이미지는 유저에게 보이지만 검사 대상이 아니었습니다. url을 파싱해 같은 판정에 태우고, 받기는 공인 IP · http(s) · 20MB · 30초로 제한해 사내 주소에 닿지 않게 했습니다.

## 결과

- 채팅 이미지 평가셋(191장) 성인 여부 판정 **탐지율 96%, 오탐률 0.7%**(ROC-AUC 0.998), RTX 4090 단건 기준 이미지 1장 **0.2초**로 목표(업로드 직후 1초 이내) 충족
- 운영팀(버블챗·팅글) 검수 보조 도구로 사내 운영 중이며, 첫 하루치 1,310장을 실패 없이 분류(278장 약 2분 30초, 동시 8건)
- 운영팀 피드백을 판정 규칙 v5~v7로 반영해 과판정 감소(버블챗 block 109 → 41장)
- 운영팀은 block 이미지 모아 보기와 어드민 바로가기를 가장 좋게 평가했고, 운영자가 고친 라벨은 정답 데이터로 쌓이고 있음

## 남은 것

- 사전 측정은 기준값을 같은 데이터에서 골라 낙관적이고, 채팅 이미지라 캐릭터 이미지와 분포가 다릅니다. 실제 검수 대상의 라벨·사유 정밀도는 운영자 검토가 쌓이는 대로 측정합니다.
- 사유 태그 표를 규정 문서에서 손으로 옮겼습니다. 규정에서 프롬프트를 생성하는 것이 다음 단계입니다.
- 검열 API와 어드민 연동은 기획을 마쳤고, 개발팀과 진행할 단계입니다.
