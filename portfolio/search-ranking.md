# 검색 랭킹 개선과 평가 체계

> 품질을 한 번도 측정한 적 없던 검색에 평가 기준선부터 세우고, 검색 대상 필드와 인기도 두 축을 다시 설계한 뒤 개선폭과 리스크를 함께 계량한 작업.

- 기간: 2026.09
- 소속: (주)버블탭 AI코어팀
- 역할: 단독 설계·구현·실험
- 사용 기술: OpenSearch, BM25, Nori/N-gram Analyzer, LLM-as-judge, Python, 층화 추출, Bootstrap

## 문제

월 15만 건 규모의 질의가 들어오는 검색인데, **품질을 잰 적이 한 번도 없었다.** 질의-노출-클릭 로그가 남지 않아 기준선 자체가 존재하지 않았고, 그래서 "무엇이 문제인가"부터 추측에 의존하고 있었다.

들여다보니 원인은 세 겹이었다.

#### 색인에는 있는데 쿼리가 보지 않는 필드

태그·작가명·상세설정은 이미 색인돼 있었다. 화면 카드에도 태그가 보인다. 그런데 검색 쿼리가 그 필드를 조회하지 않았다.

| 질의 `순애` | 건수 |
|---|---|
| 실제 검색 결과 | 41 |
| 그 태그가 달린 문서 | **1,314** |

#### 상위 10건의 절반이 조각 매칭

단어·형태소·태그 어느 쪽으로도 전체 일치가 없고, ngram 조각으로만 걸린 문서가 상위 10건의 **49%** 를 차지했다(캐릭터 탭). 한 글자까지 쪼개는 ngram 설정 때문에 검색어의 첫 글자만 공유하는 문서가 상위권을 채우는 일이 흔했다.

#### 실제 이용량이 순위에 전혀 반영되지 않음

텍스트 점수가 곧 최종 점수였다. 텍스트 유사도가 비슷한 문서들 사이에서 무엇을 위로 올릴지에 대한 기준이 없었다.

## 접근 순서

개선안을 먼저 만들지 않았다. 잴 수 없으면 무엇을 바꿔도 좋아졌는지 알 수 없기 때문에, 순서를 뒤집었다.

```
[1]  기준선 만들기: 로그가 없으니 평가 파이프라인부터
     · 검색량 분위 4개 층으로 층화 추출한 질의 796개
     · 질의당 상위 20건을 LLM 이진 판정(13,934건)
    │
    ▼
[2]  원인 분해: 결과 0건 질의 142건을 필드 단위로 분해
     · "어떤 필드를 열면 몇 건이 살아나는가" 를 먼저 측정
    │
    ▼
[3]  두 축 설계
     · 텍스트 유사도   검색 대상 필드 7개 → 15개
     · 인기도          5개 feature 를 0~1 점수로 결합
    │
    ▼
[4]  리스크 계량: 순위 이동 행렬로 "얼마나 흔들리는가" 확인
     · 인기도 가중치를 기본값 0.3 → 0.1 로 하향
    │
    ▼
[5]  악화 원인 분리: 인기도만 적용한 회차를 따로 실행
     · 나빠진 질의의 범인을 필드와 인기도로 갈라냄
    │
    ▼
[6]  사각지대 측정: 전체 검색의 19.7% 인 비한국어를 따로 측정
     · 개선이 닿지 않은 이유를 구조로 규명
```

## 기술 의사결정

### 비교 전에 실서비스 재현부터 맞춘 이유

개선 전후를 비교하려면 "개선 전" 결과부터 실제 서비스와 같아야 한다. 로컬 재현 환경이 실서비스와 다른 결과를 내면, 개선폭이 개선 때문인지 재현 오차 때문인지 가를 수 없다. 출발점에서 실서비스와 상위 10건이 겹치는 비율은 33.1% 였다.

| 단계 | 캐릭터 일치도(@10) |
|---|---|
| 출발점 | 33.1% |
| 측정 조건 맞추기(성인 제외·노출 범위) + 결과 기반 추정 튜닝 | 78.5% |
| 개발팀의 운영 검색 코드 문서대로 쿼리 이식 | **83.1%** |

세계관은 91.6%, 씬은 89.3% 까지 맞췄고, 로그인 검색은 번역 필드와 국가 설정 조건까지 옮겨 45.8% → 75.3% 가 됐다. 다만 늘어난 50.0p 중 가장 큰 몫은 알고리즘이 아니라 **측정 조건을 맞춘 것**(성인 제외만 +21.8p)이었고, 보고에도 그렇게 적었다.

남은 차이를 가중치로 더 좁히기 전에 상한부터 쟀다. 같은 질의로 운영을 8회씩 호출해 보니 **운영끼리도 96~98% 만 겹쳤다.** 원인은 삭제 대기 문서가 원본·복제본별 idf 통계를 다르게 만드는 것으로, 로컬에서 재현해 확인했다. 남은 차이는 데이터 시점과 운영 쪽 통계 차이라 가중치로는 맞출 수 없다고 보고 튜닝을 멈췄다.

### 개선이 아니라 평가를 먼저 만든 이유

로그가 없다는 건 단순히 데이터가 없다는 뜻이 아니라, **개선했다고 주장할 근거가 영원히 안 생긴다**는 뜻이었다. 그래서 첫 작업을 "사람이 클릭하지 않아도 품질을 잴 수 있는 대체 지표 만들기"로 잡았다.

- **층화 추출**: 질의를 검색량 분위 기준 4개 층으로 나누고, 검색량이 많은 층에서 더 많이 뽑았다. 평균을 낼 때는 층별 검색량 비중으로 되돌려 가중한다. 실제 사용자가 겪는 품질에 가깝게 재기 위해서다.
- **판정자에게 숨긴 것**: 순위·점수·인기도·어느 회차인지를 모두 가렸다. 이름·소개글·태그·작가명만 주고 "이 검색어와 관련 있는가"만 이진으로 판정하게 했다.
- **같은 잣대 보장**: 개선 전후를 같은 프롬프트로 다시 판정했다. 같은 (검색어, 문서) 쌍은 한 번만 판정하고 두 회차가 공유한다.

### 필드를 감으로 고르지 않고 0건 질의로 역산한 것

"태그를 넣으면 좋아질 것 같다"는 추정으로 필드를 늘리면 나중에 무엇이 효과를 냈는지 설명할 수 없다. 그래서 결과가 0건인 질의 142건을 먼저 전수 분해했다. 문자열이 어느 필드에 들어 있는지, 그 필드가 지금 검색 대상인지를 갈라 보니 원인이 나뉘었다: 한 글자라 색인어가 안 만들어진 것, 언어 필터에 걸린 것, 검색 대상이 아닌 필드에만 있는 것.

이 분해에서 **비검색 필드를 열기만 해도 9%가 살아난다**는 수치가 나왔고, 그게 필드 확장의 근거가 됐다.

같은 시기에 "색인 실패"로 의심되던 무결과 질의 90건도 전수 확인했다. 색인·분석기를 고쳐서 살아나는 문서는 0건이었다. 색인은 정상이었고, 원인은 한 글자 질의·성인/언어 필터·검색 필드 설정이었다.

다만 이건 후보를 고르는 근거였지, 남길지를 정하는 근거는 아니었다. 8개 필드를 한꺼번에 넣고 전체 효과만 보면 무엇이 효과를 냈는지 알 수 없어서, **필드를 하나씩만 더한 회차**를 따로 돌려 기여를 갈랐다.

| 추가한 필드 | Precision@10 기여 |
|---|---|
| 태그 (전체 일치) | **+3.2p** |
| 태그 (부분 일치) | **+2.9p** |
| 작가명 | +0.7p |
| 상세설정 (캐릭터 설정·기타 설정) | ±0 |
| 전부 | +5.0p |

0건 질의를 살려낸 건 상세설정 필드였는데, 정작 상위 10건의 정확도에는 아무 기여가 없었다. 결과 건수만 늘고 정답은 늘지 않은 것이다. 그래서 **평가는 15개 필드로 했지만 적용안에서는 상세설정을 빼고 11개로 확정**했다. 넣을 이유가 있다는 것과 남길 이유가 있다는 것은 다른 문제였다.

같은 회차에서 성인·공개·국가 조건이 `must`·`should` 절에 있어 점수에 가산되던 것도 찾았다. 조건은 점수와 무관해야 하므로 `filter` 절로 옮겼다.

### 인기도를 곱하지 않고 "남은 여지"에만 더한 이유

인기도를 반영하는 가장 흔한 방법은 텍스트 점수에 곱하는 것이다. 실제로 초기 회차에서 `텍스트점수 × (1 + 2 × 인기도)` 형태를 먼저 시도했는데, 오히려 품질이 떨어졌다. 곱셈은 텍스트 점수가 높은 문서일수록 보너스를 크게 받아서, **이미 잘 맞히고 있는 1페이지를 인기도가 재정렬**해 버리기 때문이다.

그래서 구조를 바꿨다.

```
AS-IS   최종점수 = 텍스트점수

TO-BE   최종점수 = rel + W × 인기도 × (1 − rel)          W = 0.1

        rel = 텍스트점수 ÷ 그 검색어의 1위 텍스트점수     (0~1)
```

`rel` 이 1 에 가까운 문서, 즉 확실히 관련 있는 상위권에는 `(1 − rel)` 이 0 에 가까워 인기도가 거의 개입하지 못한다. 반대로 텍스트 점수가 애매한 구간에서만 인기도가 자리를 가른다. **관련성이 확실한 곳은 건드리지 않고, 판단이 어려운 곳에서만 실제 이용량을 참고한다**는 원칙을 수식으로 박아 넣은 것이다.

1위 점수로 나누는 정규화가 먼저 필요했던 이유는 텍스트 점수의 크기가 **질의마다 최대 18배** 달랐기 때문이다. 1위가 5점인 질의도, 89점인 질의도 있어서 인기도를 고정값으로 더하면 질의마다 영향력이 제각각이 된다. 반면 10위 아래로는 인접 순위의 점수 차가 0.03 수준이라, 인기도가 순서를 가르는 구간이 자연스럽게 그쪽에 생긴다.

구현에서 한 번 걸린 함정이 있다. `rel` 의 분모인 1위 점수를 구하는 1차 쿼리에 개선 전 필드셋을 그대로 쓰면 분자만 커져 `rel` 이 1 을 넘고, 상한에 걸려 상위권이 전부 `rel = 1` 로 뭉치면서 인기도가 아예 작동하지 않았다. 두 쿼리가 같은 필드셋을 보도록 고쳐야 결합식이 의도대로 움직인다.

### 가중치를 기본값 0.3 이 아니라 0.1 로 낮춘 근거

`W` 를 얼마로 둘지는 품질 지표만 봐서는 정해지지 않는다. 지표가 조금 올라도 1페이지가 통째로 뒤집히면 서비스에는 사고다. 그래서 **개선폭이 아니라 순위 이동을 기준으로** 정했다.

| `W` | 기존 1페이지 유지 | 1페이지 → 50위 밖 | 1페이지 중 새 문서 |
|---|---|---|---|
| 0.3 | 75% | **7%** | 12% |
| **0.1** | **86%** | **1%** | 4% |

인기도 점수의 실측 최댓값이 0.92 라 `W=0.3` 이면 보너스 상한이 +0.28 이 된다. 20위권 문서의 `rel` 중앙값이 0.2~0.4 인 상황에서 이 값이면, **텍스트 점수가 0 에 가까운 인기 문서도 1페이지를 밀어낼 수 있다.** 그 여지를 없애는 선이 0.1 이었다.

### 가중치를 자동으로 찾지 않은 이유

필드 가중치와 `W` 를 베이지안 최적화 같은 자동 탐색으로 정하는 방안도 검토했지만 접었다. 자동 탐색은 최적화할 목표 함수가 있어야 하는데, 클릭률처럼 사용자 행동에서 나오는 신호가 하나도 없는 상태였다. LLM 판정을 목표로 삼으면 판정 잡음에 가중치가 맞춰질 위험이 있고, 무엇보다 실패 사례를 열어 보면 방향이 분명해서 자동 탐색 없이도 조정이 가능했다. 그래서 판정 결과와 순위 이동 행렬을 보며 손으로 정했다. 행동 로그가 쌓이면 그때 자동 탐색으로 넘어가는 것이 순서다.

### 인기도 점수의 상한을 고정 상수로 두지 않은 이유

인기도는 5개 feature 를 가중합해 만든다.

```
인기도 = 0.40·f(최근 30일 이용자) + 0.30·f(누적 좋아요) + 0.15·f(누적 댓글)
       + 0.10·급상승 + 0.05·신선도

f(v)   = min(1, log(1+v) / log(1+상한))      ← log max 정규화
급상승  = (7일 활동/7) ÷ (30일 활동/30) 을 0~1 로
신선도  = 0.5 ^ (공개 후 경과일 / 30)         ← 30일 반감
```

가중치 합이 1 이고 각 항이 0~1 이므로 **인기도는 수식적으로 0~1 이 보장된다.** 결합식에서 `W` 가 곧 보너스 상한이 되려면 이 보장이 먼저 필요했다.

핵심은 `f(v)` 의 **상한을 고정 상수로 두지 않은 것**이다. 상한은 그 서비스·그 도메인·그 항목의 실제 분포 상위 1%(P99)로 잡고 주 1회 갱신한다.

- 도메인마다 활동량 자릿수가 다르다. 같은 상한을 쓰면 활동량이 작은 도메인이 통째로 0점 근처로 눌린다.
- 매번 다시 계산하면 점수가 흔들려 순위가 요동친다. 그래서 주 1회로 고정했다.
- 상한에 하한선(10)을 뒀다. 데이터가 적을 때 상한이 1~2 로 내려가 점수가 과열되는 것을 막는다.
- 값이 전부 0 인 항목은 빼고 남은 가중치를 비율대로 키워 합을 1 로 맞춘다.

### 샤드를 5개에서 1개로 줄인 이유

색인당 문서가 수만 건 규모라 샤드를 다섯으로 나눌 이유가 없었다. 분할의 이점은 없고 부작용만 남는다. BM25 의 IDF 는 샤드 단위로 계산되므로 같은 단어라도 샤드마다 점수가 달라지고, 환경마다 샤드 구성이 다르면 여기서 맞춘 가중치가 프로덕션에서 재현되지 않는다. 샤드 수는 색인을 만든 뒤에 바꿀 수 없어서 프로덕션 적용안에 1개로 못 박았다. 색인 갱신은 증분 색인에 주 1회 전체 색인을 더하는 방식으로 정했다. 인기도 배치가 전체 문서를 갱신하는 직후에는 삭제 표시된 옛 문서가 세그먼트 병합 전까지 IDF 통계에 남아 통계가 일시적으로 두 배가 되므로, 배치 뒤 삭제 문서만 정리하는 강제 병합을 붙이도록 운영 절차에 적었다.

### 개선폭이 아니라 "얼마나 흔들렸나"를 같이 낸 것

필드를 두 배로 늘리고 새 점수 축을 더하는 변경이라, 지표가 올랐다는 것만으로는 배포 판단을 할 수 없었다. 같은 검색어의 같은 문서가 어디로 이동했는지를 전수로 집계했다.

| 기존 순위 ＼ 변경 후 | 1~10 | 11~20 | 21~30 | 31~40 | 41~50 | 50위 밖 |
|---|---|---|---|---|---|---|
| **1~10** | **81%** | 12% | 3% | 2% | 1% | **2%** |
| **11~20** | 6% | **58%** | 18% | 6% | 4% | 9% |
| **21~30** | 1% | 8% | **47%** | 20% | 8% | 17% |
| **31~40** | 1% | 3% | 9% | **38%** | 19% | 31% |
| **41~50** | 1% | 2% | 3% | 9% | **34%** | 52% |

행 합이 100% 다. 아래로 갈수록 유지율이 81% → 58% → 47% → 38% → 34% 로 떨어진다. **위는 지키고 아래를 섞는** 구조이고, 기존 1페이지에서 50위 밖으로 밀려난 문서는 2% 에 그쳤다. 반대로 변경 후 1페이지의 11% 는 기존에 50위 밖이던 문서이며, 그중 상당수는 기존 쿼리로는 **매칭조차 되지 않던** 문서다.

### 악화를 뭉개지 않고 범인을 가른 방법

필드 확장과 인기도 도입을 한 번에 적용했기 때문에, 나빠진 질의가 생겼을 때 어느 쪽 탓인지 알 수 없었다. 그래서 **인기도만 적용한 회차**(필드는 그대로, `W=0.1`)를 따로 실행해 세 회차를 나란히 놓고 비교했다.

| 범인 | 건수 | 비중 |
|---|---|---|
| 인기도: 인기도만 넣어도 이미 그만큼 나빠짐 | **22** | 76% |
| 필드 추가: 인기도로는 설명되지 않음 | 7 | 24% |

즉 이번 변경의 부작용은 대부분 필드가 아니라 인기도에서 왔다. 개별 사례를 열어 보면 더 분명하다. 어떤 질의는 1~3위 점수가 0.68 이상인데 4위부터 0.09 이하로 떨어졌다. 이 구간의 점수는 거의 **인기도 몫만으로 만들어진 것**이고, 텍스트 유사도가 1위의 10% 미만인 문서가 자리를 산 셈이다.

이 분해 덕분에 후속 과제가 "인기도를 줄이자"가 아니라 **"텍스트 유사도가 일정 수준 미만이면 인기도 가산을 주지 않는 하한선을 둔다"** 로 구체화됐다.

### 통계적으로 유의하지 않은 구간을 그대로 표기한 것

질의마다 난이도가 달라서, 표본을 다시 뽑으면 개선폭이 달라질 수 있다. 층 안에서 **질의 짝을 복원 추출**하는 층화 부트스트랩을 2,000회 돌려 95% 신뢰구간을 냈다. 짝을 유지하므로 질의별 난이도 차이가 상쇄된다.

신뢰구간이 0 을 걸치는 조합은 "효과 없음을 배제하지 못한다"로 보고 표에 그대로 남겼다. 6개 조합 중 하나가 1페이지 기준으로 여기 걸렸는데, 판정 깊이를 20위까지 넓히면 유의해졌다. 효과가 없었던 게 아니라 **첫 열 자리에 덜 도달했다**는 해석이 가능해졌다.

여섯 조합을 동시에 판단하므로 다중비교 문제도 확인했다. 본페로니 보정으로 각 구간을 99.17% 로 넓혀도 여섯 곳의 판단은 그대로였고, 부트스트랩 없이 층화 표준오차 공식으로 낸 구간과도 결론이 같았다. 하위 층 표본이 작아 분산이 다소 과소추정되는 한계는 문서에 남겼다.

### nDCG 대신 DCG 를 순서 지표로 둔 이유

순서까지 반영하는 지표로 처음엔 nDCG 를 썼다. 그런데 nDCG 는 **그 검색 결과 안의 정답으로 만든 최선값**으로 나누기 때문에, 정답을 1건만 찾아 1위에 두면 나머지 4건이 틀려도 만점이 된다. 정답 4건을 1~4위에 모은 결과와 구분되지 않는다. 사용자가 느끼는 품질은 "정답을 몇 개나 위에 보여줬나"인데, nDCG 는 "찾아온 것을 얼마나 잘 정렬했나"만 본다.

그래서 정규화하지 않은 **DCG@K 를 주 순서 지표**로 두고 Precision@K 와 나란히 보고했다. DCG 는 질의마다 만점이 달라 절대값 비교는 어렵지만, 같은 질의의 개선 전후를 짝으로 비교하는 이 설계에서는 그 약점이 문제가 되지 않는다.

### 형태소 분석기가 원인이라는 가설을 반증한 방법

비한국어 검색 품질이 낮은 원인으로 한국어 형태소 분석기가 지목되고 있었다. 한자를 한국어 한자음으로 읽어 복합어를 잘못 쪼개는 건 사실이었다.

그런데 해당 분석기 필드를 통째로 제거하고 800개 질의를 다시 돌려보니 **순위가 바뀐 질의가 2개뿐**이었다. 필드별 점수 중 최댓값 하나만 쓰는 랭킹 구조에서, 가중치가 높은 기본 필드가 분석기 필드를 항상 이기기 때문에 **깨진 토큰이 애초에 순위에 닿지 못하고 있었다.** 분석기는 병목이 아니었고, 여기에 시간을 쓰지 않기로 했다.

### 임베딩을 대체가 아니라 보완으로 본 이유

상위 10건의 절반 가까이가 ngram 조각 매칭이었고, `재벌`·`캠퍼스` 같은 장르·설정어는 글자가 정확히 같아야만 잡혔다. 의미 비교로 이 구멍을 메울 수 있는지 캐릭터 질의 100개로 파일럿을 돌렸다.

| BM25 대비 | Precision@10 변화 (95% CI) |
|---|---|
| 임베딩 단독 | −2.7p [−7.0, +1.6] |
| BM25 + 임베딩 · 가중합 0.5:0.5 | +2.7p [+0.1, +5.6] |
| BM25 + 임베딩 · RRF | **+4.4p [+1.9, +7.2]** |

임베딩 단독은 BM25보다 나빴다. 특히 1위 관련률이 61.3% → 48.8% 로 떨어졌다. 둘을 함께 쓸 때만 효과가 났으므로 임베딩은 BM25를 대체하는 축이 아니라 보완하는 축이다. 첫 시도(문장 유사도용 모델, 소개글만 임베딩)는 실패했고, 검색용 모델로 바꾸고 이름·소개를 함께 넣고서야 효과가 났다. 성패를 가른 것은 결합 가중치가 아니라 모델과 임베딩 대상 텍스트였다.

효과는 확인했지만 임베딩 모델을 서빙할 GPU 서버가 부족해 이번 적용안에는 넣지 않았다.

## 결과

측정은 한국어 질의 796개 · LLM 판정 13,934건 기준이다.

|  | AS-IS | TO-BE |
|---|---|---|
| 검색 대상 필드 | 7개 | 평가 **15개** → 적용 **11개** (태그·작가명 추가, 기여 없는 상세설정 제외) |
| 태그 부분일치 | 전체 일치만 | **부분일치 색인 추가** |
| 성인·공개·국가 조건 | 점수에 가산 | **`filter` 절로 분리** |
| 인기도 | 없음 | **5개 feature 결합, `W = 0.1`** |
| 검색어 없는 첫 화면 | 없음 | **인기도순 정렬** |
| 인프라 | 샤드 5개 · managed 서비스 | **샤드 1개 · 검색 서버 이중화 · 증분 색인 + 주 1회 전체 색인** |

- **Precision@10 +3.6 ~ +6.8p**: 6개 조합 중 5개 통계적 유의(나머지 1개는 +2.3p로 오차 범위 안). 판정 깊이 전체(@20) 기준으로는 6개 전부 유의
- **DCG@10 +6 ~ +27%**: 순서까지 반영해도 6개 조합 전부 유의. 정답이 늘었을 뿐 아니라 위로 올라왔다
- **개선 질의 153건 : 악화 질의 29건 = 5.3 : 1**: 세 탭 591개 질의 기준. 나머지 409건은 그대로
- **인기도가 실제로 작동했다**: 상위 10건 중 최근 30일 이용자가 0명인 문서가 51% → 39% (캐릭터·버블챗)
- **조각 매칭이 밀려났다**: 전체 일치 없이 ngram 조각으로만 걸린 문서가 상위 10건의 49% → 44% (캐릭터·버블챗). 없앤 게 아니라 태그 필드가 더 높은 점수를 내며 아래로 밀어낸 것이다
- **기존 1페이지의 81% 유지 · 50위 밖 이탈 2%**: 변경 규모 대비 순위 안정성 확보
- 효과는 **탐색형 질의**에 집중. 조건에 맞는 것을 둘러보는 질의(`다인물` 0.1 → 0.9, `연예인` 0.2 → 0.9, `동양풍` 0.3 → 1.0)에서 크게 올랐다. 이번에 추가한 필드의 핵심이 태그이고, 태그가 곧 탐색형 질의의 정답이기 때문이다

특정 대상 하나를 찾는 지칭형 질의는 Precision 상승폭이 작았는데, 이건 개선 실패가 아니다. 해당 인물이 두 건뿐이면 상위 10자리를 채울 방법이 없다. 그래서 지칭형은 DCG 처럼 순서를 반영한 지표로 따로 봐야 한다. 정답이 두 건이라도 그 둘이 맨 위에 있으면 검색은 제 역할을 한 것이다.

## 이 개선이 닿지 않은 곳

위 결과는 전부 한국어 질의다. **실제 검색의 19.7% 는 비한국어인데 한 번도 측정된 적이 없었다.** 따로 표본을 뽑아 약 32,000건을 추가 판정했다.

|  | 한국어 | 비한국어 |
|---|---|---|
| Precision@10 변화 | **+2.3 ~ +6.8p** | −0.6 ~ +2.1p |
| 통계적으로 유의한 조합 | **5 / 6** | **0 / 12** |

신뢰구간이 전부 0 을 걸친다. 효과가 없었다고 봐야 한다.

원인은 랭킹이 아니었다. **태그에 번역본이 없다.** 검색 쿼리를 만드는 코드가 번역 세트를 이름·소개글에만 붙이기 때문에, 이번에 추가한 8개 필드가 비한국어 사용자에게는 **하나도 적용되지 않는다.** 랭킹이 나빠서가 아니라 개선이 적용된 적이 없는 것이다.

대신 훨씬 크게 움직이는 변수를 찾았다: 사용자의 **국가 설정에 따른 노출 범위**다. 검색 코드를 한 줄도 바꾸지 않고 이 설정만 바꿔도 Precision@10 이 6.7p 까지 움직였다. 원본 문서가 적은 언어권일수록 글로벌 문서에 기대는 몫이 커서 영향이 컸다.

이 측정에서 평가 규칙 자체가 하나 교정됐다. 비한국어 질의는 **국가를 그 언어로 설정한 사용자 기준으로 재야 한다.** 한국 기준으로 재면 해당 언어권 원본 문서가 결과에서 빠져 품질이 실제보다 나쁘게 나온다. 실제로 한 언어권은 한국어보다 품질이 높았는데 그동안 반대로 보고돼 있었다.

## 남은 과제

- **인기도 가산 하한선**: 텍스트 유사도가 일정 수준 미만이면 인기도를 주지 않는 floor 도입. 악화 원인의 76% 가 여기서 왔다
- **한국어 형태소 분석의 원형 손실**: 상위 검색어의 33% 가 형태소 분석에서 원형을 잃는다(`좀비` → `비`). 비한국어에서는 병목이 아니었지만 한국어 쪽은 분석기 필드 가중치 조정을 측정할 차례다
- **태그 번역 또는 다국어 동의어 사전**: 비한국어에 개선이 닿게 하려면 랭킹이 아니라 이쪽을 손대야 한다
- **질의-노출-클릭 로그 적재**: 이번에는 LLM 판정으로 대체했지만, 로그가 쌓이면 CTR·평균 랭킹 지수라는 온라인 지표로 검증할 수 있고 나아가 랭킹 모델 학습 데이터가 된다
- **BM25 + 임베딩 하이브리드 검색**: 파일럿에서 BM25 대비 Precision@10 +4.4p(RRF)를 확인했지만, 임베딩 모델 서빙에 필요한 GPU 서버가 부족해 다음 단계로 넘겼다
- **프로덕션 반영 및 온라인 A/B 테스트**: 변경안은 확정됐고, 실서비스 적용은 진행 예정이다
